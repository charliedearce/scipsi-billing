# Online billing rebuild: planning baseline

Status: LIFECYCLE, DOCUMENT-STUDIO, PRICING, REGISTRATION, PWA, COMMUNICATION AND DOCUMENT-HISTORY DESIGN APPROVED; implementation remains phased; existing foundation scaffold retained. Updated: 2026-09-19.

BIR readiness: **COMPLIANCE READINESS PLANNED**, confirmed by the user on 2026-09-17 for the online billing rebuild. Compliance controls are part of the phased development scope, not a claim of implemented, tested or BIR-approved functionality. See [compliance plan](docs/BIR_COMPLIANCE.md) and [current execution status](docs/PROGRESS.md).

The user selected Vue UI, Laravel API, and PostgreSQL as the direction for recreating SCIPSI Billing online. An initial Art Design Pro/Laravel scaffold exists; domain workflows remain planned. On 2026-09-19 the user approved the lifecycle baseline, then added the central Document Studio, versioned tariff/fuel-surcharge rules, configurable VIP late charges, SkySMS-backed transactional customer/VIP messages, required customer registration identity/contact fields, PWA readiness, Admin in-app announcements, and auditable document history. W20-W37 record the accepted workflow baseline. This approval does not authorize production migration or resolve taxpayer-specific accounting, privacy, security or provider inputs.

Customer bank-deposit overpayment now has an online payment-credit ledger: teller-confirmed excess is retained for the customer's next checkout, where it reduces the combined bill amount before a residual bank instruction is issued. It is separate from VIP borrowing credit and does not create a refund workflow. See [implementation evidence](docs/evidence/P3-05-CUSTOMER-PAYMENT-CREDIT.md) for verified paths and remaining acceptance gates.

## Project location

This `online-billing/` directory is the root for the future Vue/Laravel/PostgreSQL application. It contains planning/discovery documents, synthetic fixtures, discovery scripts, Docker development data services, and the Phase 1 application scaffold under `apps/`. The Vue shell is based on [Art Design Pro](https://github.com/Daymychen/art-design-pro) (MIT-licensed); its demo pages and mock data are retained only as a visual foundation and are not billing functionality. Proposed `contracts` paths in the architecture are relative to this directory. Legacy source paths cited in these documents are relative to the parent billing repository.

Frontend contribution standard, directed by the user on 2026-09-21: all AI agents must preserve Art Design Pro as the single UI/UX system for `apps/web`. Before a visual change, agents must read [.agents/skills/art-design-pro-ui/SKILL.md](.agents/skills/art-design-pro-ui/SKILL.md), reuse the existing components and theme tokens, and avoid introducing a parallel generic dashboard design. `AGENTS.md`, `CLAUDE.md`, `.claude/skills`, and GitHub Copilot instructions expose this requirement across agent runtimes.

## Improvements prioritized for the rebuild

2026-10-05 hosting decision: the user selected Coolify on the `scipsi.com` VPS. The current deployment at `staging.scipsi.com` is an isolated technical staging exercise using synthetic data; it does not authorize the Phase 6 pilot or production cutover. See [deployment evidence](docs/evidence/P1-04-STAGING-DEPLOY.md).

| Existing behavior/evidence | Proposed improvement | Proof required |
| --- | --- | --- |
| Invoice items can precede headers; header and number consumption are separate (`BillingMod`, `BillingAddMod`) | Draft header owns draft items; posting transaction commits snapshots, number, audit, and outbox together | Failure injection leaves no partial posting; retries return the same document |
| Number reservations use operator names in pools | Explicit series/register, transactional allocation, uniqueness, user IDs, optional expiring reservations | Two clients cannot issue the same number |
| OR allocations can precede receipt header (`ORAddMod`, `ORBillnoModule`, `frmPartial`) | Receipt posting locks affected invoices and validates current collectible balances | Concurrent partial payments cannot over-allocate |
| Financial rules read controls and grid positions | Pure decimal calculation services with versioned rules and fixtures | Legacy examples match at every calculation stage |
| Print flags participate in edit authorization | Separate financial lifecycle, approval lifecycle, artifact state, and print attempts | Reprint or failed PDF generation cannot change financial balances |
| Approved deletion can restore numbers (`NewAdminMod`) | Preserve issued numbers and linked reversals; only unused drafts may be discarded | Decision W07 approved and correction scenarios reconciled |
| SQL/procedure definitions are absent from the repository | Capture source schema; use reviewed PostgreSQL migrations and constraints | Reproducible empty setup and repeatable migration rehearsal |
| Per-workstation layouts | Central published template versions, captured on issuance | Later designer changes do not alter historical reprints |
| Broad USER/ADMIN roles and text audit | Named permissions, location scoping, structured audit, requester/approver separation | Direct API authorization and cross-location tests |
| Global controls and `tbl_settings` mix operational and financial behavior | Typed configuration by owner and scope; domain-critical rules are versioned separately; secrets stay in deployment secret storage | Unauthorized/stale updates fail, changes are audited, and posted documents retain the settings/rules used |

The source evidence is summarized in the existing documentation and can be traced to `Modules/BillingMod.vb`, `Modules/BillingAddMod.vb`, `Modules/ORAddMod.vb`, `Modules/ORBillnoModule.vb`, `OR/frmPartial.vb`, `Administrator/NewAdminMod.vb`, and the `DocPrint` template services.
