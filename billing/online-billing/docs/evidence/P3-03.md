## Implementation and evidence

- Added `document_correction_requests` and append-only `document_correction_request_events` with restrictive target/actor/revision foreign keys, exactly-one-target and distinct-requester/reviewer checks, and partial unique indexes for active target/action requests.
- Added request, independent decision and stale-target validation. A request freezes the target document revision hash and lock version; approval locks and rechecks the original invoice/receipt and latest immutable revision. A stale target returns a conflict instead of acting on stale facts.
- An issued-unpaid invoice can request `INVOICE_CORRECTION`; an invoice with posted receipt allocation is rejected from that path. A posted receipt can request `RECEIPT_REVERSAL` review. Approval creates no replacement document and performs no receipt reversal, allocation edit, certificate-capacity edit, balance change, number allocation, or artifact rewrite.
- Added scoped endpoints: `GET/POST /api/v1/document-correction-requests` under `corrections:request`, plus approve/reject routes under `corrections:approve`. A request may use the printed invoice/collection-receipt number without losing zero padding, or the internal ID for an existing API client; exactly one resolves and locks the organization-scoped target.
- Added the Teller/Administrator **Document Corrections** workspace. It filters request status, submits a visible document-number review request, shows only the operational target/reviewer/timeline fields, and permits an independent Administrator decision only. It clearly states that a decision does not execute a fiscal correction or receipt reversal.
