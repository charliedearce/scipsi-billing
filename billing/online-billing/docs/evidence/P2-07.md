## Task Summary

Implemented and verified **Customer billing requests and fair teller queue** ([Decisions W21, W22, W26, W27, W31](../discovery/CUSTOMER_SERVICE_LIFECYCLE.md), [`PHASES.md`](../PHASES.md), and [`CUSTOMER_SERVICE_LIFECYCLE.md`](../discovery/CUSTOMER_SERVICE_LIFECYCLE.md)). Key deliverables:

- **Complete Submission Auto-Admission ([Decision W21](../discovery/CUSTOMER_SERVICE_LIFECYCLE.md))**:
  - Customers create draft billing requests selecting customer account, service type, and location.
  - Required document types configured in [`DocumentRequirement`](file:///h:/SCIPSI-BILLING/billing/online-billing/apps/api/app/Models/DocumentRequirement.php) are validated upon submission.
  - Submissions without required or clean files are rejected with detailed validation messages.
  - Once complete and clean, the request is automatically admitted to the queue, assigning:
    - Stable transaction reference number: `REQ-YYYYMM-XXXXXX` (never consuming fiscal series).
    - Monotonic queue ticket number: `ticket_number` via [`QueueTicket`](file:///h:/SCIPSI-BILLING/billing/online-billing/apps/api/app/Models/QueueTicket.php) per organization and location.
    - Frozen document requirement snapshot (`requirement_snapshot`).
    - Immutable initial submission timestamp (`initial_submitted_at`) for priority ordering.
- **Fair FIFO Queue with Original Priority Retention ([Decision W22](../discovery/CUSTOMER_SERVICE_LIFECYCLE.md))**:
  - Queue ordering is strictly driven by `(initial_submitted_at ASC, ticket_number ASC)`.
  - When a teller requests document correction (`NEEDS_CORRECTION`), the request is temporarily set aside for customer revision.
  - Customer uploads clean replacement versions ([`PrivateFileVersion`](file:///h:/SCIPSI-BILLING/billing/online-billing/apps/api/app/Models/PrivateFileVersion.php)) and resubmits.
  - Upon resubmission, `initial_submitted_at` is **strictly preserved**, retaining the customer's original queue priority so they do not lose their place to newer submissions.
- **Atomic Oldest-Eligible Claim ([Decision W22](../discovery/CUSTOMER_SERVICE_LIFECYCLE.md))**:
  - Tellers claim the next eligible request via database row locking (`SELECT FOR UPDATE SKIP LOCKED`).
  - Cherry-picking is prevented: requests are atomically handed out in strict FIFO priority order.
  - Sets active teller assignment with lease timestamps.
- **Assignment Lease Heartbeat & Inactivity Recovery**:
  - Teller sends periodic heartbeat (`POST /api/v1/teller/billing-requests/{id}/heartbeat`).
  - If a teller disconnects or abandons a claimed request beyond a threshold (e.g. 15 minutes), `recoverStaleAssignments()` recovers the request back to `QUEUED`, clearing assignment fields while retaining `initial_submitted_at`.
- **Cross-Day Carryover**:
  - Because priority is keyed on `initial_submitted_at` rather than a day-reset counter, requests pending at the end of the day carry over into the next business day at the head of the queue, ahead of all same-day submissions.
- **Bill-Ready Integration & Idempotency ([Decisions W26, W31](../discovery/CUSTOMER_SERVICE_LIFECYCLE.md))**:
  - Teller prepares invoice draft (`prepareBillingDraft`), transitioning the request to `BILLING_IN_PROGRESS`.
  - When the invoice is posted via `InvoicePostingService`, `completeBillReady()` marks the request `BILL_READY`, links `invoice_id`, creates customer in-app notification, and emits an `INVOICE_ARTIFACT_READY` outbox notice.
  - Repeated calls or retries are strictly idempotent, never creating duplicate invoices, notifications, or fiscal postings.
- **Customer Security Boundary**:
  - Cross-tenant and foreign customer access is strictly forbidden with HTTP 403 Forbidden.
