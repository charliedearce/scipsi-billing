## Implementation and evidence

- Added PostgreSQL receipt posting source, receipt, tender, allocation and withholding-application records with foreign keys, restrictive financial deletion, uniqueness and settlement lookup indexes.
- `ReceiptPostingService` locks in the required order: durable source identity, customer, invoice IDs ascending, certificate IDs ascending, then the collection-receipt series. It reuses the same receipt for an identical source retry and rejects a changed payload for an already-used source key.
- The service re-runs `SettlementCalculatorService` against locked balances, posts only confirmed/cleared cash-like tenders, consumes withholding capacity only for the returned amount actually applied, records explicit unapplied surplus, allocates an immutable collection-receipt number, and creates document revision/audit rows in the same database transaction.
- `ReceiptIssuanceArtifactService` freezes a collection-receipt payload and creates a server-rendered canonical PDF/hash after commit. The seeded `COLLECTION_RECEIPT` series and Studio layout are digital-only; no physical device printing was added.
- Added `POST /api/v1/receipts`, guarded by `receipts:post` and the existing request-idempotency middleware.
- Added a two-process PostgreSQL stress harness. Two worker processes are released from a shared start barrier with distinct source keys and the same fully payable invoice. Both recorded confirmed funds receive unique receipt numbers, but row locking permits exactly one `receipt_allocations` row for the invoice; the second full amount is preserved as the explicit unapplied collection instead of over-allocating the invoice.
