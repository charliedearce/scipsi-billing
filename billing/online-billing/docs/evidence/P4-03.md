# P4-03: reports and exports — implementation evidence

Evidence date: 2026-09-20. Status: **IN_PROGRESS**.

## Implemented initial vertical

`GET /api/v1/reports/billing-collections` and its CSV export provide the first scoped web reporting vertical: the **Billing & Collections Register**. It reads issued invoices and collection receipts as separate activity streams for the caller's organization and authorized location scope. Supported filters are business-date range, location, customer, invoice status and receipt status. The response retains exact decimal strings and groups totals by currency; it does not subtract activity streams into a balance.

The export endpoint has an independent `reports:export` permission, a 10,000-row guard before pagination/export, a UTF-8 BOM, formula-prefix neutralization for spreadsheet safety, and an append-only `BILLING_COLLECTIONS_REPORT_EXPORTED` audit event containing its filters, row count and content SHA-256. The Vue screen is visible to Teller and Administrator role bundles and uses the same API scope for filtering, pagination and authenticated Blob download.

This is an operational register only. It is **not** a customer statement or aging result, fiscal/BIR book/export, revenue-recognition result, VAT reconciliation, print artifact, or proof that legacy Crystal report output has parity. Physical printing remains deferred.

## VIP principal-aging export slice

`GET /api/v1/reports/vip-credit-aging/export?as_of=YYYY-MM-DD` adds a second, deliberately narrow P4-03 export. It reuses P3-09's immutable credit-charge terms and effective posted-receipt allocation cutoff logic to produce a UTF-8, spreadsheet-formula-safe CSV at an explicit Asia/Manila date.

- Export requires `credit_aging:export` **and** current `Administrator` authority. Credit accounts are organization-level in the current data model; until an authoritative location mapping exists, a Teller cannot receive an organization-wide export merely by being assigned the named permission.
- The CSV includes account/customer, invoice, currency, charged-business date, captured due-date/terms, days/bucket, charged principal, applied-at-cutoff, and outstanding principal. It contains no payment proof, bank reference, receipt artifact, payer snapshot, contact, provider, or live calculation payload.
- `VIP_PRINCIPAL_AGING_EXPORTED` is append-only and records only the report code, cutoff/timezone, organization-wide Administrator scope, account/row counts, `late_charges_included=false`, and content SHA-256. It does not put customer rows into the audit event.
- P3-11 late charges are excluded. This export is not a fiscal/BIR book, collection receipt, settlement, payment proof, PPA release, or accountant-approved late-charge report.
- The staff aging screen defaults its cutoff from the Asia/Manila calendar day, not the browser's UTC date; the server remains authoritative for a request without an explicit cutoff.

## Communications operations aggregate slice

`GET /api/v1/reports/communications-operations` and the Administrator **System > Communications Operations** dashboard add a separate, read-only operational aggregate. The default period is the most recent 30 Asia/Manila calendar days; explicit ranges have a 93-calendar-day maximum. The route uses the existing `sms_deliveries:view` permission and does not create an export, provider request, audit event, notification or financial command.

- An Administrator receives organization-scoped transactional-SMS status/event-key counts, a `provider_failed` plus `unknown_reconciliation_required` follow-up count, and current/in-period organization announcement aggregates. A Teller with that permission receives only delivery counts whose immutable event source location intersects their assigned locations; unscoped account events and organization-wide announcement aggregates are withheld.
- The payload deliberately contains no phone/contact/customer value, message content/hash, template/policy, provider queue/message identifier, raw observation, invoice, receipt, payment, tax, PPA or fiscal value. It states `message_content_included=false` for every caller. `provider_sent` remains a provider-reported status, not delivery/read/payment/receipt proof.
- Added reporting indexes on `notification_deliveries (organization_id, created_at)` and the per-version announcement seen/acknowledged/dismissed timestamps. These support the aggregate only; they do not change the notification/announcement lifecycle.
- During implementation, announcement reads, mutations and authoring were tightened to the actor's organization: Administrator authority no longer bypasses tenancy, request `organization_id` is prohibited, and audience role/location IDs must be global-or-own-organization and own-organization respectively. This is an authorization correction, not a change to financial behavior or a cross-organization support workflow.
