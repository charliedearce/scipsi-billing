# P4-04: Document Studio lifecycle administration — retirement and branding-asset evidence

Evidence date: 2026-09-20. Status: **IN_PROGRESS**.

## Implemented slices

The Document Studio now has a protected template-version retirement workflow:

- `POST /api/v1/admin/document-studio/templates/{templateId}/versions/{versionId}/retire` requires `templates:retire`, idempotency protection and a non-empty reason.
- Retirement locks the version and refuses it while an active current or future route still references that version. An Administrator must publish and activate a replacement before retiring a routed layout.
- Retirement changes only the version to `RETIRED` and records the timestamp. It does not delete the JSON layout, template history, document snapshot or existing canonical PDF/artifact.
- An append-only `DOCUMENT_TEMPLATE_VERSION_RETIRED` audit event records actor, reason, before/after status, template identity and version number.
- Published and retired versions cannot be validated or published again; a retired version cannot be activated. The activation endpoint also rechecks template, location and document-series organization scope before it resolves a version.
- The Admin Studio provides a reason prompt and makes retired/published layout JSON read-only. Preview remains available for historical layout review.

This is a document-administration action, not a billing, receipt, payment, fiscal correction or physical-print action. It never recalculates an amount or changes an issued artifact.

### Private branding assets

- `GET/POST /api/v1/admin/document-studio/assets`, authorized private download, and reasoned retirement are scoped to the caller organization. Upload/retirement require `templates:assets:manage`; metadata/download require `templates:view`.
- Upload accepts structurally valid PNG/JPEG images only (2 MB, maximum 4096px each dimension), stores a SHA-256-addressed payload on `local_private`, and never returns the storage path. SVG, remote image URLs and arbitrary source payloads are excluded.
- A JSON layout image requires a positive `asset_id`; the service rejects cross-organization, missing, or retired assets on ordinary draft creation/update/validation. Image rendering obtains the asset internally under the template organization and retains Dompdf remote fetch protection.
- `DOCUMENT_TEMPLATE_ASSET_UPLOADED` and `DOCUMENT_TEMPLATE_ASSET_RETIRED` are append-only audit events. Retiring does not delete the source: existing published versions, frozen snapshots and failed-artifact retries can still render. A fork may carry an old reference solely so an operator can replace it before saving.
- The Admin Studio now has a Branding Assets tab, upload/retirement dialogs, and an active-asset selector that inserts a safe image element into a writable draft. Image output needs the supported Docker PHP runtime's GD extension; it is now installed in `apps/api/Dockerfile`.

### Ordinary Studio lifecycle audit

- Successful administrator actions now record `DOCUMENT_TEMPLATE_CREATED`, `DOCUMENT_TEMPLATE_VERSION_DRAFT_CREATED`, `DOCUMENT_TEMPLATE_VERSION_DRAFT_UPDATED`, `DOCUMENT_TEMPLATE_VERSION_VALIDATED`, `DOCUMENT_TEMPLATE_VERSION_PUBLISHED`, and `DOCUMENT_TEMPLATE_ACTIVATED` in addition to the existing retirement and asset events.
- Draft update audit snapshots preserve the complete before/after layout definition and validation state. Activation records the activated route plus identities and prior state of the matching route activations it replaced.
- Creation plus its initial draft are one database transaction, so a rejected initial layout cannot leave an unaudited template without a version. The automatically invoked validation inside publication remains functional but does not emit a second `VALIDATED` event; the explicit validation action remains distinguishable in history.
- Preview, list and show stay read-only and generate no business audit records.
