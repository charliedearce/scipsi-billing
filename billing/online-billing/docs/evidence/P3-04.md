## Implementation and evidence

- Added `ReceiptReversalService` executed only from an APPROVED `RECEIPT_REVERSAL` correction request via `POST /api/v1/document-correction-requests/{id}/execute` (`receipts:reverse`).
- Execution locks request -> receipt -> invoices -> certificates, marks the receipt `REVERSED` without deleting allocations/tenders/numbers/PDF, restores withholding certificate capacity once, writes an immutable `document_correction_links` REVERSAL row, appends receipt revision/audit, and marks the request `EXECUTED`.
- Retry of an executed request returns the same reversed receipt and does not restore capacity a second time.
- `ReceiptPostingService` now counts only allocations from `POSTED` receipts when computing prior settlement, so a reversed receipt no longer blocks a new source-keyed collection.
- After a successful first reverse, a local `RECEIPT_REVERSED` notification event/outbox intent is queued for an active linked portal user (receipt number + generic action label only; no provider call). Duplicate execute does not create a second event.
- Invoice correction execution and fiscal replacement documents remain intentionally out of this slice.
- Document Corrections UI adds an execute path for approved receipt-reversal requests.
